# PostgreSQL persistence v1

Migration `0001_hosted_contracts.up.sql` defines the initial authoritative
hosted state. Later additive migrations extend its lifecycle, artifact, and
browser-session records without reinterpreting existing rows. UUIDs are
generated by the control plane, so the schema requires no database extension.
Database time is used for leases, retries, retention, and transition
timestamps.

## Authority

`runs` owns ingestion readiness and validated identities. `job_inputs` owns the
immutable normalized request. `jobs` owns current lifecycle and exact terminal
artifact identity. `job_attempts` records monotonic attempts and leases.
`outbox` transports transactional notifications. `audit_records` is an
append-only description of meaningful events, not a state-reconstruction log.
Distinct jobs with the same normalized request share one immutable `job_inputs`
row; idempotency keys determine whether the job itself is reused or newly
created.

`artifacts` records immutable object key, version, digest, size, schema,
retention, and the attempt that produced it. Canonical result JSON remains in
that immutable object. PostgreSQL stores its bounded summary and provenance,
not another JSONB copy of the semantic result.

`browser_sessions` stores only keyed token and CSRF verifiers, scopes, expiry,
revocation, and bounded usage metadata. A session belongs to one workspace and
cannot outlive its fixed short expiry.

Migration `0007_active_run_digest.up.sql` preserves workspace-local digest
uniqueness for every active run while releasing the digest when a run reaches
`deleted`. Deleted rows and their historical references remain intact; a new
upload receives a new run and object key rather than resurrecting history.

Workers have no database role. Only the control plane performs mutations.
Publishers and reconcilers use separate least-privilege roles in deployment but
still call the same conditional state transitions.

## Enforced invariants

Composite foreign keys bind run inputs to one workspace. One job row has one
nullable current attempt number, which references its own attempt. Attempt
primary keys make numbers unique and positive. Artifact object key and version
are globally unique. A terminal success requires an authoritative artifact;
other terminal states cannot have one. State and shape checks reject invalid
operation inputs.

Database constraints cannot alone make terminal rows immutable. Every mutation
uses a transaction and predicates on `state`, `row_version`, current attempt,
and lease where applicable. A successful update increments `row_version` and
writes its required audit or outbox row before commit. Zero affected rows means
the caller lost the race and must read current state rather than guess.

## Migration policy

Applied migration files are immutable. Startup reads a migration ledger and
refuses an unknown future schema. Forward migrations include compatibility
tests from every supported prior version and an explicit rollback procedure.
The initial migration is reversible only while no retained hosted data is
needed; its down migration drops every hosted table and type and is therefore
an operator-approved destructive rollback, never an automatic repair.

Verification may report broken references, expired leases, stranded outbox
rows, and orphan objects. It does not silently repair them. Reconciliation uses
narrow version-checked transitions and audits every authoritative repair.
